Parallel Inference, Serial Side Effects: Eliminating Information Inconsistency in Multi-User Collaborative Coding on a Single Shared LLM Agent Session

Wondeuk Yoon†  and  Dujeong Lee†
†Samsung Electronics, Suwon, Republic of Korea
{wondeuk.yoon, dujeong.lee}@samsung.com

Abstract—When several knowledge workers each drive their own AI coding-agent session, their contexts silo and diverge, reproducing — now at the agent layer — the classic organizational pathology of information inconsistency: a collaborator instructs the agent to do B when the team needed A, because no participant sees the whole. Persistent personal and company-wide memory stores only partially help: propagation is eventually-consistent and human-curated, so it fails precisely when people work the same problem at the same time. We argue the structural fix is to collapse the N siloed sessions into one shared agent session — a single live process, a single shared conversation context, and a single workspace — that every collaborator attaches to. Inconsistency then becomes impossible by construction. The obstacle is that a naïve single shared session serializes concurrent input behind one active turn and a FIFO queue, producing head-of-line (HOL) blocking: one user's long build freezes the whole room. We present a concurrency contract — parallel inference, serial side effects — that decouples the two halves of an agent turn: LLM reasoning for each user's message runs as an independent, immediately-streamed turn (eliminating HOL), while every file write, tool execution, and context commit passes through a single per-sandbox serial executor (eliminating lockless concurrent writes to the shared workspace). Because each user's message is an independent turn rather than one batched with others, faults are isolated: a malformed or adversarial input fails within its own turn instead of poisoning a shared inference. We detail the supporting mechanisms (per-turn multiplexing with turn-scoped interrupts, snapshot-read + completion-order serial context commit, strict 1:1 question-answer attribution, active-turn-count session state, a concurrency cap with a fair round-robin overflow queue, and an opt-in gate fixed at post creation), and report end-to-end measurements from a working proof of concept (Aidit-Code). With the contract enabled, two users' answers begin streaming near-simultaneously and finish 92 ms apart; with it disabled, the second answer starts only after the first completes, 3.3 s later.

Index Terms—Collaborative software engineering, large-language-model agents, multi-user concurrency, head-of-line blocking, shared execution context, sandbox isolation, real-time fan-out, serialized side effects, pessimistic concurrency control.

I.  Introduction

Coordinated knowledge work has long been organized as a tree: a manager fans tasks out to several practitioners who each execute a slice in relative isolation. The structure scales headcount but it pays a recurring tax. Practitioners need to be hired and managed; more corrosively, the lateral channels are thin — managers talk to managers, while the practitioners who actually do the work rarely see how the whole is moving. The result is information inconsistency: a practitioner, working from a partial and stale picture, confidently produces B when the team had already converged on A. The error is not incompetence; it is a structural consequence of siloed context.

The arrival of capable code agents — large language models (LLMs) that call shell, file, and package tools to write and run software [3], [4] — changed the unit of labor but not this pathology. Today a practitioner is amplified by an agent rather than replaced by one, and the natural usage pattern is that each person opens their own agent session. Two collaborators working the same repository now hold two independent agent conversations, with two divergent contexts. When one steers their agent down a path the other cannot see, the team again ends up with B instead of A — the old inconsistency, relocated to the agent layer and, if anything, accelerated by the agent's productivity.

The industry's current answer is persistent memory: per-user "personal memory" and shared "company-wide memory" stores (e.g., memory.store-style mechanisms) that an agent can read and write. These help across time — what one session learns, a later session can recall. But they do not solve concurrency. Two problems persist. First, memory is not shared in real time: while two people work the same task simultaneously, neither session's in-flight reasoning is visible to the other, so they still diverge during the very window that matters most. Second, promoting a useful fact from personal to company-wide memory is human-mediated: a person must notice it, curate it, and publish it. The human becomes the propagation bottleneck, and the system is only as consistent as that person is timely.

Thesis. If the disease is divergent context across many sessions, the cure is to stop having many sessions. We collapse the per-user silos into a single shared code-agent session — one live agent process, one shared conversation context, one workspace directory — that all collaborators attach to. Every command, every answer, and every file change flows into and is absorbed by the same authoritative context that everyone observes in real time. Under this construction, two collaborators cannot hold inconsistent pictures of the work, because there is exactly one picture. Information inconsistency is eliminated not by better synchronization but by removing the thing being synchronized.

The obstacle. A single shared session is easy to describe and hard to make usable. The straightforward implementation accepts one input at a time: it keeps a single active turn and serializes the rest behind a FIFO queue (or, worse, a "busy" gate that rejects or preempts in-flight work). With one active turn, output is effectively one stream. This serialization collides head-on with collaboration. If user A starts a multi-minute build, user B's one-line question cannot even begin until A finishes: it is stuck behind the queue head. The essence of collaboration — each participant getting their own answer concurrently — is exactly what the serial model forbids. We call this head-of-line (HOL) blocking, and it is the reason naïve shared sessions are abandoned in favor of per-user isolation in the first place.

Contribution. We resolve the tension with an asymmetric concurrency contract we call parallel inference, serial side effects. The two halves of an agent turn have opposite safety requirements, so we treat them oppositely. Inference — the LLM completion stream — is embarrassingly parallel and has no shared mutable state, so each user's message becomes an independent turn that begins and streams immediately, regardless of anyone else's work; N answers stream at once and are fanned out to everyone. Side effects — file writes, tool/shell execution, and commits to the shared context — do touch shared mutable state, so every one of them is funneled through a single per-sandbox serial executor and applied one at a time. Reasoning never blocks; mutation never races. Concretely, this paper contributes:

  • A framing of multi-user agent collaboration as an information-consistency problem, and the argument that a single shared session is the structural (not merely convenient) solution (§II).
  • The parallel-inference / serial-side-effects concurrency contract that makes a single shared session usable under real concurrency by eliminating HOL blocking while preventing concurrent-write corruption (§IV).
  • The supporting mechanisms required to make the contract correct: per-turn turnId multiplexing with turn-scoped interrupts; shared-context snapshot read + completion-order serial commit that preserves tool-call/tool-result pairing; strict 1:1 question–answer attribution with no input batching; active-turn-count session state; a concurrency cap with a fair round-robin overflow queue; one-active-turn-per-user; and an opt-in gate fixed once at post creation (§IV).
  • A working proof-of-concept implementation (Aidit-Code) and an end-to-end evaluation on a live LLM backend showing HOL elimination, enforced concurrency caps, preserved per-user serialization, correct real-time attribution, and per-turn fault isolation under adversarial input (§VI).

The remainder of the paper motivates the consistency problem (§II), gives a system overview (§III), specifies the concurrency contract and its mechanisms (§IV), describes the implementation (§V), evaluates it (§VI), surveys related work and the two axes on which we differ — sharing instead of isolation, and conflict prevention instead of conflict detection (§VII) — and discusses honest limitations (§VIII).

II.  The Information-Inconsistency Problem

A. Three regimes of the same disease

We distinguish three regimes (Table I). In the pre-agent regime, a manager coordinates several human practitioners; communication is hierarchical and lossy, and practitioners act on partial pictures. In the per-session-agent regime — today's default — each practitioner pairs with a private code-agent session. Throughput rises, but each session is a fresh silo of context; the lateral channel between practitioners is now also a lateral channel between divergent agent contexts, and nothing reconciles them while work is in flight. In the shared-session regime we propose, all practitioners drive one agent over one context; the lateral channel is the context itself.

B. Why persistent memory is insufficient

Personal and company-wide memory stores are valuable, but they are a temporal mechanism: they carry knowledge from a past session to a future one. Two limitations make them unable to prevent same-time inconsistency. (i) No in-flight sharing. A memory store records completed facts; it does not stream one session's partial, in-progress reasoning into another. While Alice and Bob both work the build at 10:03, neither store reflects what the other is doing at 10:03. (ii) Human propagation bottleneck. A fact discovered in personal memory only becomes team-wide after a human curates and promotes it. The system's consistency is gated on a person's attention and timeliness; under load that person is exactly who is too busy to curate. A single shared session sidesteps both: there is no propagation step because there is nothing to propagate between — all work already lives in one context, visible to all, as it happens.

C. The cost of the obvious shared-session implementation

Given the case for one shared session, why is it rare? Because the obvious implementation is unusable. To keep a single agent's mutable workspace coherent, implementations admit one input at a time: a single active turn, with concurrent inputs serialized behind a FIFO queue, or a "busy" gate that rejects new input or preempts the running turn. Either way the room has one active turn and one output stream. The consequence is HOL blocking: response latency for every user is coupled to the longest in-flight task, not their own. A one-line question waits behind a package install. Preemption is worse — it truncates a collaborator's in-progress answer or file edit, and makes the session-status indicator flicker between busy and idle as the queue drains. The serial contract is therefore not a minor inefficiency; it is fundamentally at odds with multi-user parallelism, which is the whole point of collaboration. §IV reverses it.

III.  System Overview

Aidit-Code is a mobile-first web platform in which every post (a community thread) is bound 1:1 to an isolated execution sandbox, and the thread is a live code-agent session running inside that sandbox. Participants attach to the same session and observe its output in real time. Fig. 1 shows the architecture.

A. Server-key model and single-generation fan-out

Unlike a bring-your-own-key design in which each client calls the model provider directly [1], Aidit-Code hosts the agent server-side. The LLM is reached over an OpenAI-compatible interface whose API_KEY, BASE_URL, and MODEL reside solely in the server's .env and are injected into the agent process as environment; they never appear in any HTTP response, log line, or SSE event. A read-only GET /runtime exposes the model name and the base-URL host only. Cost is borne by the operator; abuse is bounded by rate limits and concurrency caps. Because the agent runs once on the server, its output is generated a single time and fanned out identically to every subscriber — the precondition for everyone seeing the same work, which per-client inference cannot guarantee.

B. Data model and a single source of truth

All chat bubbles — human messages, agent replies, tool calls, tool results, and system notices — are rows of one Message table (the transcript). Each row carries a server-assigned monotone integer seq that is unique within a post (@@unique([postId, seq])). This single ordering axis is the source of truth (SoT) for sorting, replay, and idempotency. Crucially, even though §IV lets many turns run at once, every bubble they emit still lands at a unique point on the one seq axis, so a client reconstructs the entire thread deterministically by sorting on seq — "result merging" is not a separate algorithm but an emergent property of a monotone log. Agent replies link to the human message that caused them via replyToId (1:1 attribution); tool bubbles link to a ToolCall record via toolCallId; human sends carry a clientId idempotency key. A per-post Sandbox (postId @unique) holds the isolation root path, a status, and a meta blob whose concurrentTurns flag gates the parallel path (§IV-G).

IV.  Parallel Inference, Serial Side Effects

The core of the system is a single contract applied to every post that opts in: reasoning is parallel; mutation is serial. We keep one shared session, one shared context, and one workspace, and we make exactly one thing concurrent — the per-user inference stream — while routing exactly one class of operation — externally-visible side effects — through a single serial gate. Fig. 2 is the canonical sequence.

A. Independent turns and parallel inference

Each human message is treated as one independent turn. When a message arrives with AI mode on, the server first persists it as a HUMAN bubble with its own seq and fans it out immediately (no human message is ever lost behind agent work), then injects it into the shared session as a turn that starts inferring at once, regardless of any other in-flight turn. Multiple AGENT_REPLY bubbles therefore enter the STREAMING state concurrently and stream to all subscribers. The former single-output-stream assumption is gone; N answers flow at once and HOL blocking disappears because a turn's latency is decoupled from every other turn's length.

B. The serial side-effect executor

Inference is parallel precisely because it is side-effect-free: a completion stream reads no shared mutable state. The opposite is true of file writes, shell/tool execution, and context commits, which all mutate state shared by every turn. The contract routes all of them through a single per-sandbox serial executor (a lock/queue keyed by the sandbox root). Two turns may both decide to write the same file; the executor applies their writes sequentially. We do not merge file contents — we serialize the writes themselves. The logical outcome is last-wins, but the physical outcome is always a well-formed file: there is no partial write, no torn file, no directory race, because the count of lockless concurrent writers to the shared workspace is held at zero. This is the system's file-safety boundary, and it is what lets inference be reckless about concurrency while the workspace stays coherent.

C. Shared context: snapshot read, completion-order commit

One post keeps one conversation context (convo). A subtlety of parallel inference over a shared context is that the OpenAI-compatible message protocol requires each assistant message bearing tool_calls to be immediately followed by the matching role:tool results; if two turns interleaved their writes into convo, this pairing would shatter. We avoid the hazard with two rules: each turn reads a snapshot of convo at its start and infers against that snapshot, and each turn's completion and tool results are committed in completion order through the same serial executor, as an atomic group. Pairing is preserved without locking inference. The accepted cost is staleness: turns launched at the same instant may not see each other's just-arrived input. We treat this as a deliberate trade — immediacy and file-safety in exchange for bounded snapshot staleness — and state it openly rather than hide it.

D. turnId multiplexing and turn-scoped interrupts

Inside the agent worker, in-flight turns are held in turns: Map<turnId, Turn>; each Turn owns its own interrupt flag and AbortController. The parent runtime adapter dispatches the agent process's interleaved stdout lines to the correct per-turn sink via Map<turnId, TurnSink>, and tool-call acknowledgements are routed by the pair {callId, turnId} so a result is matched to the right tool call of the right turn. Because turns are individuated, an interrupt names a turnId and cancels only that turn; another user's parallel turn is untouched. An accompanying steer string, if present, is delivered as new input to that turn alone.

E. Count-based session state

With one active turn, "is the session busy?" is a boolean. With many, it is a count. We define session state by the number of active turns: RUNNING iff active turns ≥ 1, IDLE iff 0. The same session.status event carries an activeTurns integer (a count, not a secret), surfaced to the UI as an "N tasks in progress" badge. A turn finishing while others remain in flight correctly keeps the session RUNNING, eliminating the busy/idle flicker of the serial model.

F. Concurrency cap, fair queue, and one-turn-per-user

Unbounded parallel inference would multiply token cost and server load, so each sandbox caps simultaneous in-flight turns at MAX_CONCURRENT_TURNS. Overflow is not rejected; it waits in a fair round-robin queue that, when a slot frees, admits the longest-waiting turn whose user has no active turn — preventing any single user from monopolizing the queue. Independently, a user may have at most one active turn (per-user inflight = 1): a user's second message waits for their own first to finish. Parallelism therefore arises only between distinct users, and the number of concurrent turns is naturally bounded by the number of concurrently active users. Notably, this reframes the FIFO queue: it is no longer "the serializer of all input" (the v0.1 role that caused HOL) but merely the holding area for cap overflow.

G. Opt-in gate and a single topology per post

The parallel path is off by default. It is enabled only when Sandbox.meta.concurrentTurns === true, a flag set once from the concurrent parameter of POST /posts at creation and never changed thereafter. A post is therefore either fully serial (the legacy single-active-turn / FIFO path, byte-for-byte preserved) or fully parallel for its entire life; the two topologies never mix within one sandbox. This makes adoption incremental and safe and keeps the legacy behavior available as a control group — which §VI exploits.

H. Why not the alternatives

Two tempting designs are rejected. Per-user process isolation (a separate agent/VM per user or per turn) destroys the shared context that motivates the whole system, and lets N processes write the same working directory without a lock — the worst case for file safety — while multiplying processes without reclamation. Input batching (coalescing N concurrent messages into one turn) collapses 1:1 attribution and causes query pollution: a single shared inference conflates distinct requests into cross-addressed responses and tool calls — one user's answer or shell command attributed to another — and it loses inter-user fault isolation, so a single malformed or adversarial message can derail or poison the entire turn for everyone (analyzed in §VII). It further loses per-message reasoning-effort and races the interrupt window. Only parallel-inference-plus-serial-side-effects satisfies concurrency, shared collaboration, file safety, 1:1 attribution, and per-turn fault isolation simultaneously.

V.  Implementation

The server is Node 20 + Fastify + Prisma (SQLite for the PoC, Postgres for scale); the client is React 18 + TypeScript + Vite. The agent runtime is a pi agent bound through an adapter so the runtime is replaceable. Two files carry the concurrency contract.

A. Worker multiplexing (piWorker.mjs)

The worker previously held global single state — one currentTurn, one tool-ack resolver, one mutable convo. We replaced the first two with per-turn state (a turns map keyed by turnId or a SINGLE sentinel for legacy), gave each turn its own AbortController, and routed tool acknowledgements by callId/turnId. The shared convo stays single but is committed through a promise chain (commitToConvo) that pushes each assistant.tool_calls and its role:tool results as one synchronous group, so no interleaving can break pairing. The legacy preemption rule ("new input aborts the previous turn") was removed for multiplexed turns but preserved for the SINGLE path, so non-concurrent posts are byte-for-byte unchanged.

B. Parent runtime routing (pi.ts) and the turn driver (turn.ts)

The parent adapter turned its single active-turn sink into Map<turnId, TurnSink>, assigns a turnId on send, multiplexes the stdin protocol as {type:'input', turnId, …}, and dispatches stdout by turnId; ackTool and interrupt are likewise turnId-routed. The cap, fair queue, and one-turn-per-user gates live here, keyed by sandbox and user. The turn driver reads the post's concurrent flag and, on the count-based status events, applies a small but important correction: at the moment a turn is published RUNNING it is not yet registered in the runtime's count, so the driver reports activeTurnCount() + 1; at IDLE it reports the raw count (the line pump has already de-counted). The per-sandbox serial executor is the existing withSandboxLock around tool execution, raised from per-turn to per-sandbox scope; tool/file events therefore arrive in order while tokens interleave freely.

C. Real-time surface and client

The SSE schema is unchanged except for the additive activeTurns field: agent.token{messageId, seq, delta} was already turn-scoped, so concurrent turns simply produce interleaved tokens for distinct messageIds, which the client accumulates per bubble. The frontend surfaces concurrency additively — an "N tasks in progress" badge, a "concurrent streaming (N turns)" divider, a ↳ @asker attribution micro-label per reply (the user's own question's reply is anchored and highlighted), and composer gating switched from "session is streaming" to "my turn is in flight," so a user's composer locks only while their own turn runs and never while someone else's does. Single-turn (legacy) rendering is pixel-equivalent to the pre-existing UI.

VI.  Evaluation

We evaluate on the running PoC against a live OpenAI-compatible backend (GitHub Models, gpt-4o-mini). Measurements are single-run, proof-of-concept observations intended to demonstrate the qualitative behavior of the contract — HOL elimination, cap enforcement, per-user serialization, and correct attribution — not to characterize production latency. The opt-in gate gives us a clean A/B: the same code path with concurrent off is the serial control.

A. HOL elimination (the central claim)

Two users on one post fire simultaneously — user A a long turn (enumerate 1..40), user B a short one — and we capture the agent.token stream. With the contract on, tokens interleave (observed run-length B×12 A×18 B×13 A×7, three switches), both turns' first tokens arrive nearly together (A at +4631 ms, B at +4572 ms), and the two complete within 92 ms of each other. With the contract off (control), output is strictly serial (A×24 B×15, one switch): B's first token arrives at +8312 ms, after A has already finished at +5068 ms — a completion gap of 3.3 s. The short question is freed from the long task's tail exactly when the contract is enabled (Table II, S0).

B. Cap, per-user serialization, inter-user parallelism

Using the interval between each reply's first token and its completion as a turn's "in-flight" window, we measure peak overlap (maxInflight). Two requests from the same user yield maxInflight = 1 (the second's first token at +5609 ms follows the first's completion at +4567 ms) — per-user inflight = 1. Two requests from different users yield maxInflight = 2 (first tokens at +1813/+2683 ms). Five different users against a cap of four yield maxInflight = 4 (four first tokens within +1662..+2581 ms; the fifth at +5452 ms, admitted only after a prior turn completes near +3699 ms) — the cap is enforced and overflow is queued, not rejected (Table II).

A note that itself confirms the design. Prompts that trigger tools serialize at the executor (by construction), so token-level parallelism is observable only on pure-text prompts; tool-bearing turns appear serialized even with the contract on. This is not a defect — it is exactly parallel-inference + serial-side-effects in action, and we use pure-text prompts to isolate the inference-parallelism measurement.

C. Real-time multi-stream UI (browser E2E)

Driving two browser users (Alice, Bob) on a concurrent=true post against the real LLM, we verified the live surface from the DOM: during concurrent streaming (activeTurns = 2) the header showed "◉ 2 tasks in progress," a "concurrent streaming (2 turns)" divider appeared, both AGENT_REPLY bubbles carried attribution labels (own question vs. peer), and the user's own composer was locked while a peer's turn did not block it. After completion the badge and divider disappeared, only the own-question attribution remained (single-turn rule), and the composer was released — the full lifecycle matched the specification.

D. Correctness and regression

The contract is covered by an automated suite: 117 backend tests across 30 files and 19 frontend unit tests for the pure attribution/active-turn selectors. Concurrency-sensitive suites (worker multiplexing, parent routing, cap/fair-queue, count-based status) were rerun five times in isolation with no flakes. Backend and frontend type-checks are clean, no user-facing string is hard-coded (all pass through i18n), and a redaction regression test asserts that no key material appears in responses, logs, or events — the server-key invariant holds on every parallel path.

E. Fault isolation under adversarial or failing input

Because the system never batches, a malformed or adversarial message is confined to its own turn (S4). Three runtime properties establish this, all exercised by the multiplexing test suite (arMux.test.ts): per-turn routing is non-crossing — with two concurrent turns, one turn's token stream never carries the other's content; a turn-scoped interrupt cancels only the named turn while its neighbor streams to COMPLETE; and cross-routed tool acknowledgements, keyed by {callId, turnId}, raise no error. It follows by construction that a turn whose input is hostile, or whose inference errors, marks only its own AGENT_REPLY as FAILED and can neither inject content into, mis-attribute to, nor abort a concurrent user's turn; its file writes, like any other, are serialized rather than interleaved (§IV-B). This is precisely the property a batched turn forfeits — there, a single poisoned input shares one inference with everyone (§VII) — and it is why we report fault isolation as a first-class result rather than a side effect.

VII.  Related Work

Code-interpreter LLM agents that call shell and file tools [3], [4], [5] and server-side execution sandboxes are well established, but they assume a single user and a single active task; they do not address one execution session shared and steered by many independent users, nor the concurrent-write hazard that creates. Collaborative cloud IDEs and real-time co-editing via operational transformation [6], [7] or CRDTs [8] share a document, not a live agent session, and reconcile concurrent edits by transformation or merge rather than by serializing an agent's side effects. The open-source pattern of many viewers sharing and steering one live AI session inspired both this work and its predecessor [1], but it presumes a single active turn and serial processing — the very source of the HOL blocking we remove. Contemporary group-chat agent frameworks make that contract explicit: OpenTag, a self-hosted agent that many users share inside a Slack thread, enforces a single active run per thread through a distributed lock (TTL + heartbeat) and rejects a concurrently arriving run with 409 Conflict so that "two runs never interleave events on the same thread" [17]. That is precisely the busy-gate serialization our contract inverts: OpenTag's lock exists to forbid parallel execution on a shared thread, whereas our per-sandbox lock preserves parallel inference and serializes only the side effects — and, having no execution workspace at all (tool calls and rich rendering only), OpenTag has no concurrent-write problem to solve in the first place.

Recent agent systems obtain concurrency through isolation: autonomous coding agents that run each task in its own cloud VM [12], multi-tenant platforms that partition by user/session, and personal agents that parallelize by delegating to sub-agents. All abandon a shared context to gain parallelism, which is the opposite of our goal.

A distinct prior approach keeps a single session but batches several users' queries — and the resulting tool calls — into one coalesced turn, as proposed for multi-user chat agents that merge rapid inputs. Batching is simple but induces query pollution in two ways. First, cross-request contamination: a single inference over several users' distinct requests conflates them, so the model returns a reply, or issues a tool call, that belongs to a different user than the one it is attributed to — silently breaking the 1:1 mapping and producing actions no one asked for. Second, loss of fault isolation: because all users share one inference, a single malformed or adversarial message — for instance a prompt-injection attempt — can derail, corrupt, or fail the entire batched turn, poisoning the output even for users who submitted nothing wrong. Our design batches nothing (cf. §IV-A, §IV-H): each user message is an independent turn, so distinct requests cannot cross-contaminate and a faulty or hostile turn fails in isolation without affecting its neighbors. Experiment-tracking systems such as MLflow [16] log many parallel runs but provide no shared conversational context, no side-effect serialization, and no real-time multi-user fan-out. Two cited patents — concurrent screen sharing [13] and multi-version malware-analysis sandboxes [14] — concern, respectively, displaying existing video and single-analyst threat detection, neither a collaborative shared workspace.

The closest design point is multi-principal agent coordination [11], where agents acting for different principals reconcile shared state with explicit intents, first-class conflict objects, Lamport clocks [10], and optimistic concurrency control — detecting stale state and resolving by rebase/retry [9]. We differ on two axes. (1) Sharing, not isolation: we keep a single shared agent, a single shared context, and a single sandbox, and multiplex only the users' inputs as parallel turns. (2) Prevention, not detection: rather than detect conflicts after the fact and rebase, we pass every side effect through one serial executor so concurrent-write conflicts never enter — pessimistic serialization in place of optimistic reconciliation. The distinguishing essence is the asymmetry itself: permit parallelism in reasoning, reduce all mutation to a single serial gate.

VIII.  Limitations and Discussion

We state limitations plainly. (i) Token cost. N concurrent turns consume roughly N× the tokens — the intrinsic price of concurrency, bounded by the cap. (ii) Shared-context capacity. A single shared convo fills faster under many users and will need raising or summarization. (iii) Same-file logical race. The serial executor guarantees physical file safety, but two turns writing the same file still resolve last-wins logically; a same-file-only serialization fallback could narrow this. (iv) Detached writers. A tool that spawns a detached/background process writes outside the lock; process-group teardown is needed to close this gap. (v) Snapshot staleness. Simultaneously-launched turns may not see each other's just-arrived input. These are the accepted costs of trading global serialization for immediacy and shared collaboration; none is hidden, and each suggests concrete future hardening. More broadly, the PoC's sandbox isolation is host-directory + path-escape + resource/network policy; container-grade isolation (Firecracker/gVisor) is future work, as is summarization policy for the shared context and threshold tuning for the cap.

IX.  Conclusion

Information inconsistency in collaborative work is, at root, a problem of divergent context across many silos — and capable code agents reproduce it whenever each collaborator runs a private session. We argued that the structural remedy is a single shared agent session that all collaborators attach to, making inconsistency impossible by construction, and we showed how to make that shared session usable under real concurrency with a single asymmetric contract: parallel inference, serial side effects. Reasoning runs per-user in parallel so no one's answer waits behind another's long task; side effects pass through one per-sandbox serial executor so the shared workspace never suffers a lockless concurrent write. A working proof of concept demonstrates the behavior end-to-end: with the contract enabled, two users' answers stream together and finish 92 ms apart, where the serial baseline forces a 3.3 s wait. We believe "share the session, parallelize the reasoning, serialize the mutation" is a general recipe for multi-user agent collaboration beyond coding.
